# 接管测试：确认写入通道映射（P16 Pro IXA1）

目标：**在启用真正的曲线之前，用两个明显不同的占空比钉死"写入通道号 → 物理风扇"的对应关系。**
这是 `--hardware-check` 做不到的——它按设计往所有通道写同一个值（`vec![40; N]`），同值写入无法暴露对调。

## 为什么必须先做这一步

`worker.rs` 里目标值是按下标一一对应的：

```rust
targets[i] = curve_i(s.channels[i].temperature);
h.write(&targets)                      // 内部：b[1] = i + 1，逐通道发 EC 0xC1
```

如果**写下标与读下标不同序**，就会出现"用 A 风扇的温度去驱动 B 风扇"的交叉：CPU 烧到 90°C 时，
CPU 风扇可能拿到按 GPU 温度算出来的低占空比。这不是性能问题，是过热风险。
所以第一条曲线必须是**不可能欠冷**的测试曲线，先确认映射，再谈曲线好不好。

## 测试曲线（已写入 `ClevoFanControl.x64.json`）

| | 点 | 在 75°C / 61°C 处的取值 |
|---|---|---|
| cpuCurve | 45→45, 75→50, 82→100 | 75°C ⇒ **50%** |
| gpuCurve | 45→85, 75→88, 82→100 | 61°C ⇒ **85%** |

设计要点：

- **50 与 85 差 35 个点**，且都远高于固件此刻给的 39% / 24% ⇒ 无论映射对错，两风扇都只会**更冷**。
- **82°C 以上两条都拉满 100%** ⇒ 万一忘了关接管、温度上去了，是 100% 而不是 50%，失效方向安全。
- 已知的小瑕疵：76–81°C 区间 CPU 通道给 50%，大致与固件同期水平相当，不构成欠冷。这是测试曲线，不是长期曲线。

`takeOver: false`、`softControl: false`、`autoRun: false` —— 文件本身**不会**替你开接管，也**不会**开机自启。

## 步骤

### 0. 前置
- **先看现在开着的那个界面**：它是在写入本文件之前启动的，内存里还是默认的平坦 40% 曲线。
  **不要在这个窗口里打开接管。** 关掉它（不要点「保存并应用」）。
- 关掉后重新启动（`requireAdministrator`，从管理员 PowerShell 起），让它读到新曲线：

```powershell
Start-Process -FilePath "%USERPROFILE%\Downloads\ClevoFanControl-v2.0.0-p16pro\clevo-fan-control.exe"
```

- 重开前必须没有残留实例，否则单实例互斥会报 `已有新／旧版 ClevoFanControl 正在运行`。

### 1. 开界面后核对两处
- 模式显示 **「固件自动」**。若显示「软件曲线」，说明接管是开的 ⇒ **立刻关掉**。
- 曲线编辑区应能看到上面的测试点（45/50/100 与 85/88/100），不是一条 40% 的平线。

### 2. 开监视器（另开一个管理员 PowerShell）
```powershell
cd "%USERPROFILE%\Downloads\ClevoFanControl-v2.0.0-p16pro"
python monitor.py --interval 1 --csv takeover-test.csv
```
确认它打印的读数与界面一致，再往下走。

### 3. 写
- 在界面里打开 **「软件接管」**。
- 观察 45 秒左右。预期：两个风扇**都变快**（占空比升到 50% / 85% 附近），温度略降。

### 4. 判定（看监视器的通道1占空比）

| 监视器显示 | 结论 |
|---|---|
| 通道1 ≈ **50%**，通道2 ≈ **85%** | **映射一致**，读写同序 |
| 通道1 ≈ **85%**，通道2 ≈ **50%** | **映射对调**，写通道 1↔2 与读通道反序 |
| 两通道仍 ≈ 39% / 24% | 写入被接受（`ret==4`）但 EC 未进入手动 ⇒ 该命令在本机不起作用 |
| 报 `EC 风扇 N 写入失败` | 写入被拒，记下返回码 |

### 5. 收尾（不管结果如何都做）
- 在界面里**关闭「软件接管」**。此时 `owned == true`，程序会走

  ```rust
  if (fault || stale || (!cfg.take_over && !force)) && owned && Instant::now() >= next_restore { h.automatic() }
  ```
  即发出 `SetDCHU_Data(0x69, 03 00 00 00, 4)` 恢复固件自动——**这一步同时验证了 0x69**。
- 监视器应在几秒内看到占空比回到固件自管的水平（量级回到 30–40% / 20–25%）。
- 然后关闭界面，再跑一次只读采样确认基线：

```powershell
python monitor.py --seconds 3
```

## 回退

| 情况 | 做法 |
|---|---|
| 只想停下 | 界面里关掉「软件接管」→ 程序发 `0x69` |
| 界面卡住/关不掉 | **Control Center** 里重设风扇，或直接重启 |
| 关掉接管后占空比没回来 | 说明 `0x69` 没生效 ⇒ 用 Control Center 或重启，并把这个现象记下来 |
| 彻底不要这个软件 | `schtasks /Delete /TN ClevoFanControl /F`（若开过自启）、删掉 `ClevoFanControl.x64.json` |

## 干扰源（读数异常时先排除这些）

- **FnKey.exe 正在运行**（PID 21744）。它也用同一份 `InsydeDCHU.dll`，可能周期性重申固件自动控制 ⇒
  表现为占空比被"拽回"固件值。作者机器上 FnKey 同样在跑，属于正常配置，但它是本次测试最可能的混淆项。
- **Control Center** 若在跑，它自己会写风扇曲线，会与接管互相覆盖 ⇒ 测试期间确保它没有在改风扇。
- 别在测试期间跑重负载：温度一过 82°C 两条曲线都拉满，会把"通道映射"这个观测目标冲掉。
