# 已知风险与未验证项

> 这篇是本仓库**最重要**的一篇。请在使用接管之前读完。
>
> 上游 `hardware.rs` 里有一道机型闸门。作者设它的原因只有一个：
> **`PK04` 背后 EC 固件侧的语义，静态分析无法确认。**
> 本方案为了在 P16 Pro IXA1 上跑起来，**主动拆掉了这道闸门**。
> 风险没有消失，只是转移到了下面这些地方。

---

## 1. 一句话

**接口层齐全 ≠ 语义一致。**

本机与作者机器在**软件层 / ACPI 接口层**是对得上的：

| 检查项 | 作者机器 | 本机（P16 Pro IXA1） |
|---|---|---|
| DCHU `_DSM` UUID `93f224e4-fbdc-4bbf-add6-db71bdc0afad` | 有 | **有** |
| ACPI 方法 `PK04` / `ECMD` / `CPKG` / `SCMD` / `CC30` | 有 | **有** |
| 设备 `ACPI\CLV0001\1` / `CLV0002\1` | 有 | **有**（AcpiBridge 驱动运行中） |
| `InsydeDCHU.dll` | `…7.88.1.0…` | `…7.62.3.0…`，**DLL 二进制哈希相同** |

**但这只能证明「接口在」，不能证明「语义一致」。**
接口在各机型上普遍存在，语义却可能各自不同 —— 这正是陷阱本身。

## 2. 完全未验证的项（真正的风险）

### 2.1 EC 固件侧语义

- **`0xC1` 逐通道写命令**：真实语义（哪一字节对应哪个通道、是否需要伴随命令）未确认。
- **`0x69` 恢复固件自动的位掩码**：`0x03` 这个值是否覆盖全部通道、在别的机型上是否相同，未确认。
- **`to_raw` 占空比换算的绝对标定**：写进去的原始值落在固件自己的 duty 尺度上（有两点吻合的证据，
  见 §3.2），但那是**两点相关，不是标定**。
- **缓冲区偏移**：`18+i*3` 温度 / `16+i*3` 实际占空比 / `2+i*2` 转速 —— 这套偏移在本机读出来的值
  与 Control Center 显示对得上，但**是否在所有机型上成立未知**。

这些都在 EC 固件里，**静态分析无法确认**。

### 2.2 其他

- **任何别的机器上的行为** —— 零证据。
- **「50 就是物理最大转速的 50%」** —— 没有转速计，也没有已知满转值，无法验证。
- **长时间运行** —— 从未连续运行超过数小时。
- **`Control Center` 与接管的互相覆盖** —— 未测。本机没有独立安装的 CC，但 FnKey 包里捆了 CC40。
- **`FnKey.exe` 的干扰** —— 未测（它一直在运行，也用同一份 DLL）。

## 3. 已实测的项，以及它们的边界

### 3.1 已实测（本机，有数据）

| 结论 | 证据 |
|---|---|
| 读取路径可用 | `--probe` 退出码 0，2 个通道 |
| **写入通道映射同序、无对调** | 差异化写入（ch1 目标 50%、ch2 目标 85%）：两通道各自升到**恰好** 50% / 85%，转速**各自分开动**（ch1 3213→4253 rpm，ch2 2122→6161 rpm） |
| `0x69` 恢复固件自动**有效** | 关闭接管后占空比回落到固件自管水平 |
| EC **锁存** | 程序停止写入后 50% / 85% 稳定保持 36 秒 |
| 读取稳定 | 255 次采样 0 失败，`stale` 自动回退大概率不会误触发 |
| 冷启动全路径 | 登录时窗口一闪即收进托盘，托盘有图标，接管正常 |

**关于「映射同序」这条，要特别注意它的证明力**：同样的占空比写入**无法**暴露通道对调，
所以测试刻意用了两个明显不同的目标值（50 与 85，差 35 个点）。这是这条结论成立的关键。

### 3.2 推断（合理，但未钉死）

- **`to_raw` 是同一把尺子**：基线 3213 rpm @ 39% ≈ 82 rpm/%，测试 4253 rpm @ 50% ≈ 85 rpm/%，
  两点吻合 ⇒ 写进去的值落在固件自己的 duty 尺度上。**但这是两点相关，不是标定。**
- **`to_raw` / `to_percent` 可往返**：读写同尺度，有记录但未做穷举。

### 3.3 一个数据冲突，说明「固件占空比不是温度的纯函数」

| 来源 | ch2 读数 |
|---|---|
| `takeover-test.md` 记的基线 | 61 °C / **24%** / 2122 rpm |
| `probe-output.txt` | 61 °C / **43%** / 3570 rpm |

同一温度、占空比差近一倍。`FnKey.exe` / Control Center 也在写同一块 EC。

**推论**：「和 Control Center 对得上」只是**同一时刻的一致性快照，不是标定**。
不要拿它当「我们的换算对了」的证据。

## 4. 失效方向与兜底

### 4.1 程序自带的运行时兜底

- 风扇数量必须落在 `1..=3`，温度必须落在 `1..=125`，否则**报错停止**，而不是拿垃圾值去控风扇。
- 采样/写入失败后停止曲线写入并尝试恢复自动；界面显示错误。
- 正常退出与睡眠暂停时也尝试恢复自动。

### 4.2 但**不保证**兜底能覆盖的场景

- **崩溃 / 强杀 / 驱动挂起**：EC 锁存，占空比会**停在最后那个值上**。作者明确不保证能恢复。
- 因此本机使用的曲线是**按「任意温度下都可安全长期保持」设计**的，
  就是为「进程死掉但值留在风扇上」这个场景兜底。

### 4.3 回退路径（只有两条）

1. **Fn 热键打开 Control Center** 重设风扇（本机没有独立安装的 CC，但 FnKey 的 appx 包里捆了完整 CC40）。
2. **重启。**

### 4.4 最容易误触的两条

- **「强制冷却」按下去会往所有通道写 95%，即使接管是关的。** 写入闸门是 `cfg.take_over || force`。
- **`forceTemp: 50` 是它的退出阈值，不是安全阀。**
- 另外：**上游内置的默认曲线是 45–90 °C 全部 40% 的平直线**，接管一开就是把两风扇钉在约 40%，
  到 90 °C 也不升。**不要用。**

## 5. 机型闸门被拆掉的精确后果

补丁 A 把判据从

```rust
machine.contains("NP5") && machine.contains("SN")
```

换成了

```rust
machine.contains("P16") && machine.contains("P1")   // 而 "P16" 本身含 "P1" ⇒ 等价于 contains("P16")
```

三个后果：

1. **它变成了一个子串测试，不是白名单。** 任何 SMBIOS 字符串里恰好嵌了 `P16` 的机器都会放行。
2. **作者原本支持的 `NP5x_6x_7x_SNx` 被一并移出了集合。** 两个字面量在 `.rdata` 里紧邻、
   只被两处 `LEA rcx` 引用，5 字节就地覆盖**无法避免**同时替换两者。
3. **一台真正的 NP5x/SNx 机器会被拒绝，并收到一句告诉它「本机是受支持机型」的报错** ——
   因为报错文本里的 `NP5x_6x_7x_SNx` 无代码引用，没有被（也无法被）改动。

## 6. 这台机器的固件行为（另一个独立发现）

32 线程满载温度扫描（`data/sweep.csv`，0.5 秒采样）显示：

```
fan1（CPU 通道）  75 °C → 94 °C   占空比全程 43%，转速 ~3700 rpm 不动
fan2（GPU 通道）  61 °C → 67 °C   占空比 24% → 42%，有响应
```

CPU 温度在 93–94 °C 顶住，是 **CPU 自己在降频**，不是风扇在散热。
⇒ 在高温段，**固件没有可「追平」的对象** —— 照字面追平就得写 43%，接管将毫无意义。

因此本机曲线改为锚定「不让 CPU 进降频」：90 °C 前拉满。
**代价是高负载下比原厂更吵。** 详见 [`curve.md`](curve.md)。

## 7. 如果你不是 P16 Pro IXA1 用户

**请不要使用本补丁。**

补丁脚本会在机型不符时拒绝运行。`-Force` 可以跳过，但那是你**自己承担**上面全部风险 ——
尤其是 §2.1 里那些连本机都没验证过的 EC 语义。
